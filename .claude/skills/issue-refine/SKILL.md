# Issue 詳細化

曖昧な Issue の内容を、コードベースの理解と対話モードを通じて具体的・実装可能なレベルまで詳細化する。

## Step 1: Issue の取得

- `gh issue view <number> --comments` で Issue 情報（タイトル、本文、ラベル、コメント）を取得する。URL の場合はそのまま渡す

## Step 2: コードベースの調査

Issue の内容に関連するコードを調査する:

1. **キーワード抽出**: Issue のタイトル・本文から技術的なキーワード（関数名、モジュール名、エンドポイント、テーブル名等）を抽出
2. **関連コード検索**: Grep / Glob で該当コードを特定
3. **コード読解**: 関連ファイルを Read して現状の実装を理解
4. **影響範囲の把握**: 変更が必要なファイル・レイヤーを特定

## Step 3: 曖昧な点の洗い出し

Issue の内容とコードの実態を照らし合わせ、以下の観点で曖昧な点を洗い出す:

### 要件の曖昧さ
- 「〜を改善」「〜を修正」→ 具体的にどの挙動をどう変えるのか
- 「〜に対応」→ どのケースを対応範囲とするのか
- 成功条件が明確か（何をもって完了とするか）

### 技術的な曖昧さ
- 既存コードのどこを変更するのか特定できるか
- 新規追加なのか既存変更なのか
- API の入出力仕様は明確か
- DB スキーマ変更は必要か
- 既存テストへの影響はあるか

### スコープの曖昧さ
- エッジケースの扱いが定義されているか
- エラーハンドリングの方針は明確か
- 他の機能・サービスへの影響は考慮されているか

## Step 4: 対話モードによる明確化

洗い出した曖昧な点をユーザーに提示し、**1つずつ**質問して明確化する。

提示フォーマット:

```
## Issue 解析結果

### 現状の理解
- （Issue の内容を要約）
- （関連コードの現状を説明）

### 明確にしたい点（{N}件）

**1. {質問}**
背景: {なぜこの質問が必要か、コードのどこに影響するか}
選択肢:
  a) {選択肢A}
  b) {選択肢B}
  c) その他
```

- 一度に全部聞かず、関連する質問をグループ化して 2-3 問ずつ聞く
- ユーザーの回答を受けて、さらに深掘りが必要なら追加質問する
- コードを見て自明な点は質問せず、前提として報告する

## Step 5: Issue の更新提案

対話モードで得た情報を元に、詳細化した Issue 本文を作成する。

### 更新後の Issue フォーマット

```markdown
## 概要
（1-2文で何をするか）

## 背景・動機
（なぜこの変更が必要か）

## 現状の挙動
（コードベースから把握した現状）

## 期待する挙動
（対話モードで明確化した内容）

## 技術的な方針
- 変更対象ファイル:
  - `path/to/file.py` — 変更内容の概要
- DB変更: あり / なし
- API変更: あり / なし

## 完了条件
- [ ] 具体的な条件1
- [ ] 具体的な条件2
- [ ] テスト追加

## 影響範囲
（他の機能・サービスへの影響）

## 備考
（エッジケース、制約事項等）
```

## Step 6: ユーザー承認と Issue 更新

1. 更新案をユーザーに提示して確認を求める
2. 承認を得たら `gh issue edit <number> --body "..."` で Issue を更新する
3. 必要に応じてラベルの追加も提案する

## 原則

- **コードを読んでから質問する** — コードを見ればわかることは聞かない
- **選択肢を提示する** — 自由記述より選択式の方が答えやすい
- **影響範囲を添える** — 「この決定は〇〇に影響します」と伝えることで判断を助ける
- **Issue は更新のみ** — 新規 Issue の作成はしない（`/issue-create` を使う）
