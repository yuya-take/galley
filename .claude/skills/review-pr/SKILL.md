# Review PR（指定PRのレビュー）

引数 `$1` で指定された **既存 PR** を gh 経由でレビューし、
**ユーザーの承認後に** コメントを投稿、著者の修正を確認するところまでを行う。

> ローカルの変更をレビューする場合は `code-review` / `code-review-full` を使うこと。
> このスキルは「他者が作成したリモート PR を番号指定でレビューする」用途に特化している。

引数 `$1`: PR 番号（`123`）、`#123`、または URL のいずれでも受け付ける。
URL の場合は末尾の番号を抽出して使う。

## 1. PR情報の取得

```bash
gh pr view $1              # タイトル・説明・対象ブランチ・状態を把握
gh pr diff $1              # 差分を取得
```

- PR の目的（タイトル・説明）と差分の範囲を把握する
- ファイル数が多い場合は変更ファイル一覧を先に確認し、レビュー対象を整理する

## 2. 分析

差分を以下の観点でレビューする。`.claude/rules/` の規約と整合性を確認すること。

- **バグ**: ロジック誤り、null/境界条件、例外処理漏れ、リグレッション
- **スコープ逸脱**: PR の目的と無関係な変更（参照ドキュメント再生成・無関係なリファクタ等）が混入していないか
- **規約違反**: `.claude/rules/rust-standards.md`（`galley-core` が Topcoat に依存しない、`[workspace.dependencies]` で依存管理）
- **セキュリティ**: 資料の隔離表示（別オリジン・sandbox・CSP）、CSRF/Host 検査、アップロード検査、ハードコード認証情報

必要に応じて reviewer agent を**並列で**起動して分析を補強する:
- Rust 変更 → `rust-reviewer` + `clean-arch-guard` + `security-reviewer`
- HTTP ルート・MCP ツール・画面の URL 変更 → `api-spec-reviewer` + `security-reviewer`
- DB モデル/マイグレーション変更 → `database-reviewer` + `migration-checker`
- 外部から来た PR（fork）→ 必ず `security-reviewer` も起動する

## 3. コメント下書き

指摘をファイル別・重大度別に整理する。各指摘には必ず `ファイルパス:行番号` を含める。

```
## レビュー結果（PR #<番号>: <タイトル>）

### CRITICAL（必ず修正）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### HIGH（修正推奨）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### MEDIUM（提案）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### 総合判定
- CRITICAL/HIGH がある場合: マージ前に修正を依頼
- MEDIUM 以下のみ: 軽微な提案として承認可
```

## 4. 投稿前承認（必須）

**下書きの全文をユーザーに提示し、承認を待つ。承認を得るまでコメントを投稿しない。**
（早すぎる投稿を防止するため。ユーザーが文面を編集したい場合は反映してから投稿する）

## 5. 投稿

承認後、コメントを投稿する:

```bash
gh pr comment $1 --body "<レビューコメント全文>"
```

- 章番号参照に `#数字` を使わない（GitHub で別 Issue / PR へ自動リンクされるため）

## 6. 修正確認

著者が修正をプッシュした後:

```bash
gh pr diff $1              # 修正後の差分を再取得
```

- 指摘が解消されているかを確認する
- すべて解消されていれば承認を提案する（`gh pr review $1 --approve` はユーザー判断で実行）
- 未解消があれば追加コメントを下書きし、再度ステップ4の承認フローを通す

## 注意事項

- **投稿前に必ずユーザーの承認を得る**（このスキルの最重要ルール）
- レビュー対象は PR の差分のみ。リポジトリ全体をレビューしない
- 指摘には必ずファイルパスと行番号を含める
- `#数字` は GitHub で自動リンクされるため、章番号や項目番号の参照には使わない
