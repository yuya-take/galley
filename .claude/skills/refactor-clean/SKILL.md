# /refactor-clean

引数: `$ARGUMENTS`（対象ディレクトリ。省略時はリポジトリ全体）

このスキルは削除だけを行う。書き換え（重複の統合、ラッパーのインライン化など）は振る舞いが変わる危険があり、レビューの観点も違うので混ぜない。

## 0. 前提の確認

- `git status --porcelain` で未コミットの変更が無いことを確認する。あればコミットか退避をユーザーに依頼して止める（削除の失敗を戻すときに、ユーザーの変更まで巻き込まないため）
- テストコマンドを特定し（`Makefile` / `package.json` / `pyproject.toml` / `Cargo.toml`）、一度実行してベースラインを取る。もともと失敗しているテストは控えておき、以降の判定から除く

## 1. 検出

対象が広い場合（複数サービスにまたがる、数百ファイル以上）は `refactor-cleaner` エージェントに対象を渡して検出と分類を任せる。狭い場合は、インストール済みのツールで直接検出する:

- Python: `ruff check --select F401,F811,F841 <dir>`、`vulture <dir> --min-confidence 80`（あれば）
- TypeScript: `npx --no-install knip`（あれば。未使用の export・ファイル・依存をまとめて検出できる）
- Rust: `cargo check --workspace --all-targets --message-format short 2>&1 | grep -E "never used|unused"`、未使用の依存は `cargo machete`（あれば）

ツールが無いものは Grep で「定義はあるが参照されない」ものを探す。

## 2. 分類と確認

| 分類 | 例 | 扱い |
|------|----|------|
| SAFE | 未使用 import、内部ヘルパー、使われていないテストヘルパー | 削除候補 |
| CAREFUL | コンポーネント、API ルート、ミドルウェア、メッセージハンドラー、Pydantic モデル。Galley では Axum のハンドラー・ミドルウェア、Topcoat の画面（`#[page]` / `#[layout]` / `#[component]`）、MCP のツール（`#[tool]`） | 動的参照（`importlib` / `import()` / 文字列でのルート・トピック名）、Docker Compose・スクリプト・CI、他サービスからの参照を確認できたものだけ削除候補にする |
| RISKY | 設定、エントリーポイント、共有モデルライブラリ、公開 API の型。Galley では `galley-core` の公開 API、`crates/server/src/main.rs`、マイグレーション（`crates/core/db/`） | 削除しない（報告のみ） |

分類結果を提示し、削除する範囲の承認を得る。

## 3. 削除ループ

ファイル（またはモジュール）単位でまとめて削除し、まとまりごとにテストを実行する。1 件ずつテストを回すと時間がかかりすぎるため。

1. まとまりの中の候補を削除する
2. lint とテストを実行する
3. 通ったら `git add` してステージし、次のまとまりへ進む（ステージ済みの状態が、次の失敗時に戻る地点になる）
4. 失敗したら `git restore <そのまとまりのファイル>` で直前のステージ状態まで戻す（ステージ済みの成功分は残る）。候補を半分ずつに分けて再試行し、原因の候補を特定してスキップする

未使用依存（`package.json` / `pyproject.toml` / `Cargo.toml`）の削除は最後に行い、ロックファイルを更新してからビルドとテストを通す。

## 4. 報告

```
## デッドコード削除結果
削除: 関数 N / ファイル N / 依存 N（約 N 行）
スキップ: N 件（テスト失敗 N、CAREFUL で確認不能 N）
RISKY（未削除）: 一覧
重複コードの統合候補: 一覧（このスキルでは書き換えない）
テスト: <コマンド> — ベースラインと同じ結果
```

変更はステージした状態で残す。コミットするかどうかはユーザーに任せる（`/pr` でまとめてもよい）。
