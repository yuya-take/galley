# Issue Create

ユーザーと対話モードでIssueを作成する。コードベースを調査して要件や技術的な検討事項を具体化する。

## フロー

### Step 1: ヒアリング

引数 `$ARGUMENTS` がある場合はそれを出発点にする。ない場合は「何を実現したいですか？」と聞く。

ユーザーの説明を受けて、以下を明確にするための質問を **最大3つ** 行う:
- 誰が使う機能か（ユーザー種別）
- 何を達成したいか（ゴール）
- 既存の機能との関係（新規 / 改善 / バグ修正）

質問は一度にまとめて聞く。1問1答のラリーにしない。

### Step 2: テンプレート選定

ヒアリング内容から適切なIssueテンプレートを選ぶ:

| テンプレート | 使い分け |
|-------------|---------|
| `Feature` | 新機能の追加 |
| `Bug` | 通常のバグ報告 |
| `Critical Bug` | 本番影響のある緊急バグ |
| `Refactor` | リファクタリング・技術的負債の解消 |
| `Documentation` | ドキュメントの作成・更新 |

テンプレートの格納場所: `.github/ISSUE_TEMPLATE/` に定義されている（無い場合はテンプレートなしで進める）

選んだテンプレートの構成に沿ってIssue本文を作成する。

### Step 3: コードベース調査

関連するコードを Glob / Grep / Read で調査し、以下を把握する:
- 変更が必要なファイル・モジュール
- 既存の実装パターン（同種の機能がどう実装されているか）
- 影響範囲（依存しているコンポーネント）
- 技術的な制約や注意点

調査結果はIssue本文の「技術的検討事項」「影響範囲」「対象範囲」等のセクションに反映する。

### Step 4: Issue本文の作成

テンプレートの各セクションを埋めてIssue本文のドラフトを作成する。

**ルール:**
- テンプレートの `<!--- コメント --->` は削除する
- 該当しないセクションは「なし」と記載するか、セクションごと削除する
- チェックボックスは該当するものだけチェックを入れる
- コードベース調査で得た具体的なファイルパスや実装方針を記載する
- 見積もり工数は記載しない（空欄にする）

### Step 5: ユーザー確認

作成したIssue本文をユーザーに提示し、確認を求める:

```
## Issue ドラフト

**タイトル**: {タイトル}
**テンプレート**: {Feature / Bug / ...}

{Issue本文}

---
この内容でIssueを作成しますか？修正したい箇所があれば教えてください。
```

修正の要望があれば反映し、再度確認する。

### Step 6: Issue作成

ユーザーの承認を得たら、Issueを作成する:

```bash
gh issue create \
  --title "タイトル" \
  --body "$(cat <<'EOF'
Issue本文
EOF
)"
```

作成後、Issue URLを報告する。

## 注意事項

- ユーザーの承認なしにIssueを作成しない
- テンプレートの構成を尊重する（セクションを勝手に追加しない）
- 技術的検討事項はコード調査に基づいて具体的に書く（推測しない）
- タイトルは簡潔に（50文字以内目安）
