# /dev

引数: `$ARGUMENTS`

## 0. 引数の解釈

| 指定 | 意味 | 既定 |
|------|------|------|
| `#123` / `123` / Issue URL | Issue 駆動。`gh issue view <番号 or URL> --comments` で取得 | — |
| 上記以外の文字列 | Issue なしのタスク説明として扱う | — |
| `--branch` | Worktree を作らず、カレントリポジトリでブランチを切る | Worktree |
| `--base <branch>` | 分岐元ブランチ（例: エピックブランチから切る場合） | `develop`（無ければ `git symbolic-ref refs/remotes/origin/HEAD` のデフォルトブランチ） |
| `--plan` | 計画を示して承認を待ってから実装する（大きな変更を実装の前に確認したいとき） | 計画を示してそのまま実装 |
| `--orchestrator <名前>` | `/orchestrate` から起動された作業セッションとして動く（下の「オーケストレータ配下モード」） | — |

引数が空なら、何を実装するかをユーザーに聞いて終了する。以前の `--quick` は既定の動きになったので、指定されても無視する。

### オーケストレータ配下モード（`--orchestrator` 指定時）

このセッションは `/orchestrate` が裏で起動した作業セッションで、ユーザーは常に見ているわけではない。確認や相談の相手は、ユーザーではなくオーケストレータ（指定された名前のセッション）になる。以下の手順のうち、ここに書いた点だけを読み替える。

- **連絡の方法**: オーケストレータへは `SendMessage` で送る。送ったら返事を待つためにターンを終えてよい（返事が届くと次のターンが始まる）。メッセージの 1 行目に種類（`計画` / `質問` / `影響` / `完了` / `中断`）と Issue 番号を書く
- **宛先**: 最初は `--orchestrator` の名前に送る。オーケストレータが開き直されると名前が変わるので、`宛先変更` のメッセージが届いたら、以後はその送り主に送る。そのとき、送れなかった連絡や返事待ちの連絡があれば送り直す
- **送れなかったとき**: オーケストレータが閉じていて送信に失敗したら、送る内容をそのまま出力に残してターンを終える。オーケストレータが再開すると `宛先変更` が届く
- **設計（ステップ 4）**: `--plan` の有無にかかわらず、計画にブランチ名を含めてオーケストレータに送り、承認を待ってから実装に入る（並行して動く他の作業と衝突しないかを、オーケストレータが確かめるため）。修正を求められたら直して送り直す
- **質問**: 計画にない判断が必要になったら、オーケストレータに質問を送る。権限が必要な操作や、拒否された操作の代行をオーケストレータに頼まない。permission の確認はこのセッションに出るので、ユーザーが agent view で答える
- **他への影響**: 共通の型・公開 API・DB スキーマ・設定など、他の Issue の作業に影響しうる変更をしたら、内容をオーケストレータに送る
- **`--branch` は使わない**: 裏で動くセッションでは、ユーザーが使っているチェックアウトのブランチを切り替えてしまうため。常に Worktree で作業する
- **環境ファイル**: `.worktreeinclude` に書かれたものだけをコピーする。それ以外に必要なものがあれば、オーケストレータに質問する
- **完了（ステップ 8）**: 検証とセルフレビューが通ったら、Skill ツールで `pr`（プラグイン導入時は `dev-flow:pr`）を `--base <base>` 付きで実行して PR を作る。その後、PR の URL・検証結果・セルフレビューで残った指摘・未解決の課題を、`完了` としてオーケストレータに送って終える
- **進められないとき**: 障害で先に進めない場合は、原因と試したことを `中断` としてオーケストレータに送る

## 1. 要件の把握

- Issue の場合: タイトル・本文・ラベル・コメントから、実装スコープと受け入れ条件を抜き出す
- タスク説明の場合: そのまま要件として扱う
- 完了の条件を決める: 受け入れ条件と、通すチェック（プロジェクトのテスト・lint・型チェックと、変更した振る舞いを確かめるテスト）。ステップ 6 では、これが通るまで直す
- 止まって確認するのは、読み方によって作業が大きく変わるとき（受け入れ条件が無い、仕様やプロダクトの判断が要る、など）だけにする。確認したい点を挙げてユーザーに聞き、Issue なら `/issue-refine` で詰めることも提案する。命名や、同等な実装方法のどちらを選ぶかといった細かい判断は自分で決め、計画に書いておく

## 2. ブランチ名

`<type>/<issue番号>-<short-desc>`（Issue なしなら `<type>/<short-desc>`）。英語 kebab-case、50 文字以内。

type は内容から判断する: `feat` 新機能 / `fix` バグ修正 / `refactor` / `docs` / `chore` / `perf` / `test`

例: `feat/123-add-user-auth`, `fix/456-connection-timeout`, `chore/update-ci-cache`

## 3. 作業環境の準備

まず `git fetch origin <base>` で分岐元を最新にする。未コミットの変更がある状態で `--branch` を指定された場合は、続行してよいかを先に確認する（変更が新ブランチに持ち越されるため）。

### 既定: Worktree

分岐元とブランチ名を確実に指定するため、Worktree は git で作成してからセッションを移す（EnterWorktree の `name` 指定は分岐元を選べず、デフォルトブランチから切られる）。

```bash
git worktree add -b <branch> .claude/worktrees/<branch> origin/<base>
```

続けて EnterWorktree ツールに `path: .claude/worktrees/<branch>` を渡して移動する。ツールが使えない環境では `cd` で移動する。

Worktree は新しいチェックアウトなので、gitignore されたファイルは引き継がれない。

- **環境ファイル**: リポジトリルートに `.worktreeinclude` があれば、そこに書かれた gitignore 済みファイル（`.env` など）をメインの作業ツリーからコピーする。無ければ、テストや起動に必要な `.env*` があるかを確認し、コピーしてよいかをユーザーに確認する（`.worktreeinclude` は Claude Code が自分で作る Worktree にしか効かず、git で直接作った場合は手動でコピーする必要がある）
- **依存関係**: `node_modules` / `.venv` などは空なので、テストの前に `npm ci` / `uv sync` などを実行する

### `--branch`

```bash
git switch -c <branch> origin/<base>
```

## 4. 設計

関連するコードを調べて計画を立てる。Plan モードは使わない。

- 調査範囲が広い（複数ディレクトリにまたがる、既存パターンを横断的に探す）場合は Explore サブエージェントに要件を渡し、「関連ファイル・該当箇所・既存実装の要点」だけを返してもらう。領域が独立していれば並列で起動してよい。既知のファイルを 1〜2 個読む程度なら直接読むほうが速い
- 計画には、変更するファイル、方針、完了の条件（ステップ 1）、影響範囲（API 互換性、マイグレーションの要否など）を含める。小さな修正なら数行でよい
- 計画を示したら、そのまま実装に進む。ユーザーは計画を見て、違えば止められる
- 次の場合は、計画を示してターンを終え、承認を待つ。修正を求められたら直して示し直す
  - `--plan` が指定されている
  - DB スキーマの変更、公開 API の互換性を崩す変更、データの削除や移行など、取り消しにくい変更を含む
  - Issue の範囲を超える変更が必要になる
  - オーケストレータ配下モード（承認はオーケストレータから受ける）

## 5. 実装

- `.claude/rules/` の規約と、周辺コードの書き方に合わせる
- 振る舞いを変えたら、テストも追加・更新する
- 実装に入ったあとで止まって確認するのは、計画にない判断で作業が大きく変わるとき、破壊的または取り消しにくい操作の前、自分では解消できない障害に当たったときだけにする。それ以外では、途中経過の報告や「次は〜します」という予告でターンを終えず、検証と完了報告まで進める（経過を伝えたいときは、次の作業と同じメッセージに書く）

## 6. 検証

- ステップ 1 で決めたチェックを含め、lint / format / 型チェック / テストを、プロジェクトのコマンド（`Makefile`、`package.json`、`pyproject.toml`、`Cargo.toml` を見て判断）で実行する
- 失敗したら原因を直して再実行する
- 実行できなかった検証があれば、そのことを報告に明記する

## 7. セルフレビュー

Skill ツールで `rv`（プラグイン導入時は `review:rv`）を `--inline --base <base>` 付きで呼び、自分の差分を見直す。`--inline` では、サブエージェントを使わずにメインの流れでレビューする。別のエージェントに自分の作業を検証させると、同じ確認を二重に行うことになるため。

あわせて Issue の受け入れ条件を満たしているかを確認する。見直しで見つけたバグや規約違反はその場で直し、判断が分かれるもの（設計の選択、スコープ外の改善）は報告に載せてユーザーに任せる。

## 8. 完了報告

- 変更ファイルと実装サマリー
- 検証結果（実行したコマンドと結果）
- セルフレビューの結果（修正済みの指摘／残っている指摘）
- 次のステップ: `/pr` でコミット・PR 作成。変更が大きい場合や、独立した複数観点のレビューを通したい場合は、その前に `/rv` を実行できることも伝える。Worktree の場合は、PR マージ後に `/sync` で片付けられることを伝える
